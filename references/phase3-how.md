# Phase 3 — HOW: Business Execution Plan

Defines HOW to execute the strategy confirmed in Phase 2. Takes DCP2 decisions as inputs.

---

## Tool 1: Product Architecture / Solution Roadmap

**Purpose**: Define how the product/solution portfolio evolves over the planning horizon. Ensures market entry strategy isn't invalidated by product gaps.

### Roadmap Dimensions

Map the following layers across time:

| Layer | NOW | Year 1–2 | Year 2–3 |
|-------|-----|---------|---------|
| **Hardware / Core Product** | [current product, version] | [planned additions] | [next-gen or variants] |
| **Software / Analytics** | [current software] | [planned enhancements] | [platform evolution] |
| **Regulatory** | [current clearances] | [planned registrations] | [additional markets] |
| **Clinical Evidence** | [current evidence, language] | [planned studies/cases] | [publications, KOL proof] |

### Roadmap Prioritisation Rules

1. Software/evidence tools that directly enable market entry (e.g. English-language study templates, localised outputs) take priority over next-gen hardware
2. Regulatory work must be sequenced: identify the critical path dependency for each market entry
3. "Proof of concept evidence" (case series, poster) precedes "investment-grade evidence" (RCT, peer-reviewed publication) — don't over-invest in evidence before commercial proof exists

## Tool 2: Value Net — 物流 / 金流 / 資訊流

**Purpose**: IBM's HOW phase requires explicitly designing three flows. Coverage Plan alone is insufficient. Most commonly missed tool in non-IBM analyses.

### 物流 (Product / Physical Flow)

Map the physical movement of product from manufacturer to end user for each target market:

| Market | Physical Flow |
|--------|--------------|
| [Market A] | [Manufacturer] → [Regulatory sponsor / importer] → [Distributor warehouse] → [Hospital / end user] |
| [Market B] | |

Also specify:
- Import permit / customs documentation requirements
- Product labelling / localisation requirements
- Spare parts and service parts flow
- Demo / loaner unit logistics

### 金流 (Financial Flow)

| Item | Design |
|------|--------|
| Pricing tiers | Hardware ASP / Software subscription / Service contract / Training / Study support |
| Distributor margin | % range and what services it covers |
| Payment terms | Standard T/T days; exceptions for KOL evaluation (loaner/consignment) |
| Revenue model evolution | Device-only → Device + Software → Device + Software + Service (recurring) |
| Currency / FX | Which currency invoiced; FX risk allocation |
| Collection risk | Who bears credit risk — manufacturer or distributor? |

### 資訊流 (Information / Data Flow)

| Flow Type | Design |
|-----------|--------|
| Clinical data | [How surgical case data flows from OR → software → KOL → publication] |
| Regulatory documentation | [QMS / technical file → sponsor → regulatory body] |
| Market intelligence | [Distributor monthly report → PM → product/market strategy update] |
| KOL management | [Study protocol → IRB → data collection → paper → conference] |
| Customer support | [Complaint/inquiry → remote diagnosis → spare parts → on-site] |
| Brand evidence | [Local case pack → international evidence pack → external communications] |

## Tool 3: Coverage Plan

**Purpose**: Define how customers are reached and served, market by market. Specifies Direct vs Indirect model and partner requirements.

### Coverage Plan Table

| Market | Coverage Model | Partner Type Required | Key KPI (3yr) |
|--------|---------------|----------------------|--------------|
| [Market A] | [Direct / Indirect / Hybrid] | [Specific partner profile] | [Units / Revenue / Reference sites] |
| [Market B] | | | |
| [Market C] | | | |

### Coverage Model Selection Criteria

| Situation | Recommended Model |
|-----------|------------------|
| New market, no brand presence, regulatory complexity | Indirect (strong local partner) |
| KOL-focused entry, clinical evidence building | Indirect (research-capable distributor) + direct KOL relationship |
| Large market, strategic priority, long-term investment | Hybrid (indirect for coverage, direct for key accounts) |
| Legal risk / unclear liability | Indirect only until resolved |
| Highly consolidated market (few large buyers) | Direct or hybrid |

### Ecosystem Partner Plan

For each market, list:
- Regulatory partner (Sponsor / UKRP / MAH / Registrant)
- Commercial distributor
- KOL / academic partner
- Service / maintenance partner
- Any ecosystem partners (ICG dye supplier, clinical society, training institution)

**Purpose**: IBM's ABP combines near-term action tasks (30/60/90) with structured incubation milestones that serve as go/no-go decision gates.

### Incubation Milestones (per market, per year)

**This is distinct from 30/60/90. Incubation Milestones are 12-month gates that trigger DCP reviews.**

| Market | Milestone 1 (Year 1) | Milestone 2 (Year 2) | Milestone 3 (Year 3) |
|--------|---------------------|---------------------|---------------------|
| [Market A] | [Regulatory + partner confirmed] | [First installation + KOL case] | [Reference sites + publication] |
| [Market B] | | | |

**Milestone format rule**: Each milestone must be binary (achieved / not achieved) and observable (not "make progress on"). Example:
- ✓ Good: "TGA sponsor contract signed + 1st distributor LOI received"
- ✗ Bad: "Progress made on Australian regulatory approach"

## Tool 5: DCP Decision Position Sheet

**Purpose**: IBM's Decision Check Points are structured go/no-go decisions presented to senior management. The DCP Position Sheet is the summary decision document.

### DCP Position Sheet Format

| Initiative / Market | DCP Decision | Executive Rationale |
|--------------------|-------------|---------------------|
| [Market A — Role] | **GO** | [Why: regulatory leverage + market quality + SPAN position + financial viability] |
| [Market B — Role] | **GO / Controlled Entry** | [Why and what "controlled" means] |
| [Market C — Role] | **Selective GO** | [Which niche, what constraints] |
| [Market D — Role] | **REDIRECT → Conditional GO** | [What must change for full GO] |
| [Initiative E] | **DEFER** | [Why defer and when to re-evaluate] |

### DCP Decision Definitions

| Decision | Meaning |
|---------|---------|
| **GO** | Full investment approved; proceed with coverage plan and ABP |
| **GO / Controlled Entry** | Proceed but with defined scope limit (e.g. KOL-only, no full commercial launch) |
| **Selective GO** | Enter a defined niche only; do not attempt full market coverage |
| **REDIRECT** | Current approach not viable; re-plan with different strategy before proceeding |
| **Conditional GO** | GO once a specific condition is met (e.g. legal clearance, partner confirmed) |
| **DEFER** | Do not enter now; re-evaluate at defined future date |
